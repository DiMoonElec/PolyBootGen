# PolyBootGen

Генератор зашифрованных файлов обновления `.xbin` для PolyBoot.
Поддерживает прежний формат V1 и контейнер V2 для одного устройства либо ROOT
с несколькими типами SLAVE.

## Сборка

Требуется .NET SDK 8 или новее с поддержкой сборки `net8.0`.

```powershell
dotnet build source/PolyBootGen.sln -c Release
```

В примерах ниже `PolyBootGen` — собранный исполняемый файл. Также можно запускать
`dotnet source/PolyBootGen/bin/Release/net8.0/PolyBootGen.dll ...`.

## Формат V1: совместимость старых скриптов

Команды и XML прежней версии сохраняются:

```powershell
PolyBootGen genconfig -out config.xml -flash 0x08003000 -size 118784 -devid "DEVICE"
PolyBootGen build -bin application.bin -config config.xml -out application.xbin
```

`genconfig` создаёт случайные ключи в XML и соответствующий `.inc`. При обычной
сборке используются уже имеющиеся ключи. Прежний XML содержит корневой элемент
`FirmwareConfig` и поля `EncryptionKey`, `IntegrityKey`, `FlashStartAddress`,
`FlashSize`, `DeviceID`. Команда `build` всегда создаёт `FORMAT=1`.

Образ V1: `[бинарник][0xFF до хвоста][MAC:16]`, версия в хвост не добавляется.
Внешний файл: заголовок `#POLYBOOT;PROTO=1;FORMAT=1`, зашифрованный заголовочный
блок, блоки данных и SHA256.

## Формат V2: сборка по одному XML

```powershell
PolyBootGen build-v2 -config update.xml
PolyBootGen build-v2 -config update.xml -out release/device.xbin
```

Шаблоны: [SINGLE](examples/single.xml) и [COMPLEX](examples/complex.xml).
Замените демонстрационные ключи, DeviceId, параметры памяти и пути.
Бинарники в шаблоны не включены: их нужно предварительно собрать.

Все относительные пути внутри XML, включая `Output`, разрешаются относительно
папки XML. Явный аргумент `-out` разрешается относительно текущей рабочей папки
и переопределяет `Output`. XML по-прежнему должен содержать поле `Output`.

Корень XML: `<UpdatePackage SchemaVersion="1" Format="2" Type="SINGLE|COMPLEX">`.
Имена XML-элементов и атрибутов чувствительны к регистру; значения `Type` и
`Target` принимаются без учёта регистра. Неизвестные поля отклоняются,
чтобы опечатка не меняла сборку незаметно.

| Поле пакета | Назначение |
|---|---|
| `Output` | Путь выходного `.xbin` |
| `MinUpdaterVersion` | Минимальная версия MCUUpdater, три числа `0..65535` через точку |
| `Comment` | Необязательный однострочный ASCII-комментарий; элементов может быть несколько |
| `Firmware` | Описание одной прошивки; элементов может быть несколько |

| Поле Firmware | Назначение |
|---|---|
| Атрибут `Target` | `ROOT` или `SLAVE` |
| `DeviceId` | Единый ID для текстового поля `ID` и зашифрованного заголовка |
| `BootloaderVersion` | Требуемое поколение команд загрузчика, целое число не меньше 2 |
| `ProxyVersion` | Положительное целое число; обязательно у ROOT в COMPLEX, запрещено у SLAVE |
| `Binary` | Путь к готовому непустому `.bin`; первый байт соответствует `AppBegin` |
| `VersionHeader` | Необязательный путь к заголовку C; версия записывается только в `#REM` |
| `Memory/AppBegin` | Начальный адрес области приложения |
| `Memory/AppLength` | Полная длина области приложения, включая хэш и MAC |
| `Keys/EncryptionKey` | Ключ XChaCha20-Poly1305, ровно 64 hex-символа |
| `Keys/IntegrityKey` | Ключ Poly1305 всего образа, ровно 64 hex-символа |

SINGLE содержит ровно одну секцию ROOT. COMPLEX содержит ровно одну ROOT
и хотя бы одну SLAVE. Секция SLAVE соответствует типу устройства: несколько
физических устройств с одинаковым ID используют одну секцию. Каждая секция
имеет собственные бинарник, ключи, память и хэш. Информационная версия опциональна
независимо для каждой секции.

DeviceId должен содержать 1–32 печатных символа ASCII без двойных кавычек
и быть уникальным среди секций с учётом регистра. Пробелы и `;` внутри ID
поддерживаются: поле `ID` записывается в кавычках. Пробелы по краям значений XML
удаляются. Один и тот же ID должен быть настроен в загрузчике для проверки
заголовка и ответа на команду получения идентификатора.

## Область приложения и хвост V2

Перенесите значения `BOOTLOADER_APP_BEGIN` и `BOOTLOADER_APP_LENGTH` из
конфигурации загрузчика:

```xml
<Memory>
  <AppBegin>0x08003000</AppBegin>
  <AppLength>116K</AppLength>
</Memory>
```

Адрес — десятичное число либо hex с префиксом `0x`. Длина дополнительно
допускает суффикс `K`/`k`, означающий 1024 байта: `116K`, `118784`, `0x1D000`
равнозначны. Выражения C вроде `(116UL * 1024UL)` не вычисляются.

Образ занимает ровно `AppLength` байт:

```text
[бинарник][заполнитель 0xFF][хэш исходного бинарника:16][MAC:16]
```

Пусть `end = AppBegin + AppLength` — адрес сразу после области приложения.
Хэш занимает `[end - 32, end - 16)`, MAC — `[end - 16, end)`.
Poly1305 вычисляется по первым `AppLength - 16` байтам, включая заполнитель
и хэш, и записывается в последние 16 байт. Версии в образе нет.

Хэш — первые 16 байт стандартного SHA256 исходного `.bin` без перестановки байтов.
Он рассчитывается до заполнения `0xFF`, добавления хвоста и шифрования.
Ключи, адреса, размер области приложения, случайные nonce и информационная версия
не влияют на этот хэш. Любое изменение байтов самого `.bin` меняет его идентификатор
с пренебрежимо малой вероятностью коллизии.

Для приведённого примера `end = 0x08020000`, хэш начинается с `0x0801FFE0`,
MAC — с `0x0801FFF0`. Максимальный размер `.bin` — `AppLength - 32`, то есть
118752 байта. Превышение размера является ошибкой; бинарник не обрезается.

Загрузчик читает хэш из этого места и возвращает `79 00` + 16 байт хэша после
успешной проверки MAC, либо `79 01` при её провале.
Линкер приложения должен резервировать хвост. В XML задаётся длина полной
области загрузчика, а не уменьшенная на 32 байта ёмкость приложения.

Весь образ, включая `0xFF`, делится на блоки данных по 128 байт. Шифрование,
структура заголовочного блока и блоков данных соответствуют V1; последний
неполный блок сохраняет фактическую длину. Nonce каждого блока случайный,
поэтому два запуска дают разные зашифрованные файлы.

## Необязательная информационная версия из заголовка C

Если `VersionHeader` отсутствует в секции XML, файл версии не читается и
автоматический комментарий с версией для этой прошивки не добавляется.
Если элемент задан, путь должен существовать, а содержимое — быть корректным:

```c
#ifndef FWVERSION_H
#define FWVERSION_H

#define FW_VERSION_MAJOR 0
#define FW_VERSION_MINOR 16
#define FW_VERSION_PATCH 0

#endif
```

Поддерживаются три однократных определения с десятичными целочисленными
литералами `0..65535`, комментарии `//`, `/* ... */`, обычный внешний
include guard `#ifndef`/`#define`/`#endif`. Заголовок может быть и без guard.
Выражения, условный выбор версии и переопределения не поддерживаются.
Прочитанная версия записывается только в комментарий перед первой секцией:

```text
#REM ROOT ID="DEVICE" VERSION=0.16.0
```

Для COMPLEX каждая доступная версия сопровождается своим TARGET и ID.
Изменение только заголовка версии меняет комментарий и общий SHA256 контейнера,
но не хэш бинарника и не подготовленный образ приложения.

Запускайте генератор после успешной компиляции прошивки. Он не проверяет,
что бинарник собран с указанным заголовком. Версия служит справочной информацией
и не должна использоваться утилитой обновления для пропуска записи.

## Контейнер и обработка ошибок

V2 содержит глобальный заголовок, комментарии `#REM`, секции `#FIRMWARE`
с метаданными и зашифрованными блоками, затем общий SHA256. Вместо прежнего `VER`
в каждой секции записывается обязательный `HASH`: 32 hex-символа, представляющие
те же 16 байт, что находятся в хвосте образа:

```text
#FIRMWARE;TARGET=ROOT;ID="DEVICE";HASH=BA7816BF8F01CFEA414140DE5DAE2223;BOOTLOADER=2
```

В этом примере HASH соответствует исходному бинарнику из трёх байт ASCII `abc`.
Алгоритм поля HASH фиксирован: первые 16 байт SHA256. Формат контейнера остаётся
`FORMAT=2`; старый MCUUpdater, ожидающий `VER`, с новой структурой несовместим.
Для загрузки требуется обновить и парсер, и workflow сравнения хэшей в MCUUpdater,
а также загрузчик МК. Генератор не добавляет фиктивный `VER` для обхода этой проверки.

Общий SHA256 файла отличается от HASH прошивки. Он считается
по ASCII-строкам после `Trim()`, без пустых строк и без разделителей строк;
последняя строка SHA256 исключается. Комментарии и метаданные входят в хеш.
В заголовках не используются обходные поля `META`: MCUUpdater должен содержать
исправленный разбор первого поля после директивы.

Сборка сначала проверяет все секции. Результат записывается во временный файл
рядом с целевым и заменяет целевой только после успешной записи. Ошибка
возвращает ненулевой код завершения, сообщение направляется в stderr.
Выход V2 не может совпадать с XML, бинарником или заголовком версии пакета.
В отчёте выводятся хэши, границы областей, адреса хэша/MAC и свободное место;
значения ключей не выводятся.

Генерация новых XML V2 и экспорт `.inc` для всех секций пока выполняются вручную
по шаблонам. Старый `genconfig` продолжает создавать конфигурацию V1 и `.inc`.
В текущей реализации MCUUpdater `MIN_UPDATER` читается, но не проверяется,
а ID в режиме SINGLE не сверяется с устройством.

## Проверки

Проверки запускаются отдельным консольным проектом без дополнительных тестовых
пакетов. Они расшифровывают блоки, проверяют образ, адреса, хэш, MAC, общий SHA256,
старый CLI, необязательные версии, независимость секций и некорректные конфигурации.

```powershell
dotnet run --project tests/PolyBootGen.Tests -- artifacts/test-fixtures
```

После обновления MCUUpdater для поддержки `HASH` можно проверить файлы его парсером
в Windows PowerShell, указав путь к собранному `PolyBootCore.dll`:

```powershell
powershell -NoProfile -File tests/Verify-MCUUpdater.ps1 -AssemblyPath C:/Work/MCUUpdater/source/PolyBootCore/bin/Debug/PolyBootCore.dll
```

Совместимость с парсером не заменяет проверку на устройстве с обновлённым
загрузчиком, который поддерживает 16-байтовую область хэша перед MAC.
